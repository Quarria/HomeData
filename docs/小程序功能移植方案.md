# 小程序功能移植方案

> 状态：实施中（后端已部署，待微信后台域名配置及真机登录联调）。更新日期：2026-10-28。

## 分支与部署约定（用户已确认）

- `dev` 是网站及后端的开发分支。`apps/web`、`apps/server`、服务端部署配置和影响网站／后端的共享契约修改，均在 `dev` 上实施和验证。
- `app` 是小程序开发分支，从合适的 `dev` 提交创建；`apps/miniprogram` 和仅服务于其构建的配置在 `app` 上维护。小程序前端不要求合并到 `dev`，构建后通过微信开发者工具上传微信平台，不部署到网站服务器。
- 两个分支属于同一仓库，`app` 从 `dev` 派生时会包含当时的网站和后端代码快照；这不意味着它们都要部署，也不改变 `dev` 是网站和后端的唯一开发基准。
- 如果小程序需要后端接口、认证、共享契约或网站修改，全部在 `dev` 实现并验证；`app` 通过配置调用已部署的 HTTPS API，不把 `dev` 的网站／服务端源码合入 `app`。不要把 `app` 合并回 `dev`。后端上线后记录兼容的 API 版本。
- 本地联调应明确小程序对应的后端版本；上线时先在 `dev` 部署并验证兼容 API，再上传／发布小程序。只修改小程序时无需部署网站；修改后端时依照网站发布流程部署 `dev` 服务。
- `app` 分支已创建，独立工作区位于 `D:\workspace\githubHome\HomeData-app`；该分支已按用户要求移除网站、服务端及其他无关文件，仅保留小程序工程。删除项尚未提交。

## 1. 目标与已知条件

将家常账的常用功能移植到微信小程序，第一版仅供本人和家庭成员使用；现有网站继续使用，两个客户端访问同一套服务和数据。小程序已申请，网站已有 HTTPS 访问。HTTPS 的实际域名、备案状态、证书链和小程序后台配置尚未核验。

**当前约束**：沿用现有账号体系和服务端权限；不新增自助注册、微信登录和微信支付。以现有功能为基准分批移植，不改变账目归属或家庭权限规则。具体批次可在实施前调整。

## 2. 技术判断

仓库现有网页为 Vue 3、TypeScript、Vite、Vue Router、Pinia；服务端是 NestJS、REST API、PostgreSQL，`packages/contracts` 使用 Zod 定义共享契约。账目、家庭、待办等业务规则和数据可复用，页面及浏览器接口需要适配小程序。

推荐在同仓 `app` 分支新增 `apps/miniprogram`，优先评估 Vue 3 + uni-app 编译到微信小程序，以便沿用团队熟悉的语言和部分纯 TypeScript 逻辑。**这是待验证的技术选型**：先做登录、写入和真机网络验证，再锁定版本；不要假设现有 Vue 组件、Vue Router、DOM、浏览器 `fetch` 或依赖都能直接运行。共享契约要验证小程序构建兼容性与包体积，必要时只提取纯类型和轻量校验。

个人主体不应以网页套壳作为主方案。腾讯云的说明指出个人主体无法配置该场景所需的业务域名；以微信后台当前规则为准。服务器 API 的合法域名与网页 `web-view` 的业务域名是不同配置。[腾讯云说明](https://cloud.tencent.com/document/product/1301/100434)

```text
现有网页 ───────┐
                ├── HTTPS / API ── NestJS ── PostgreSQL、私有票据存储
微信小程序 ─────┘                     └── worker（提醒、AI 任务）
```

## 3. 功能迁移清单

| 批次 | 功能 | 工作与边界 |
| --- | --- | --- |
| P0 验证 | 启动、登录、获取本人信息、读写一条测试数据 | 先验证真实设备、合法域名、会话方案和构建；不使用真实账目试错 |
| P1 家庭试用 | 账号登录／退出／首次改密；个人与家庭空间；账本列表、筛选、增改删、退款与恢复；待办增改、完成和重开；基本报表 | 复用服务端规则；移动端重做页面，保持权限和统计口径一致 |
| P2 完整日常 | 票据上传与查看；固定费用和期次；站内提醒；报表趋势和明细；个人设置 | 验证上传、授权图片访问和错误恢复；固定费用确认后才入账 |
| P3 扩展 | 家庭及账号管理、访客分享、PushPlus 设置、AI 辅助、衣柜 | 按实际需要逐项评估。可先保留网页管理入口；访客分享和外部跳转需单独设计，不能假设网页链接在小程序内可直接打开。衣柜以实施时仓库代码和独立计划为准，不预设其已完整交付 |

P1 是建议的首个家庭试用范围，不代表后续功能被永久排除。服务端已有的高级功能在网页仍按现有方式使用。

## 4. 前置准备

- [ ] 在微信公众平台确认小程序主体、AppID、管理员和开发者权限；AppSecret 不写入客户端、仓库或聊天。
- [ ] 核对小程序备案是否完成，以及现有 API 域名的 ICP 备案与接入状态；小程序备案和域名备案分别确认。备案和上架要求以平台后台及主管部门的实际要求为准。[工信部解读](https://www.miit.gov.cn/jgsj/xgj/hlwgl/art/2023/art_564bf0759d7e41d5b4aa8ce4996b9e84.html)
- [ ] 在个人主体可选服务类目中核对记账、待办等实际服务是否适用，记录类目及审核要求；不预先承诺审核结果。
- [ ] 确认小程序要访问的 API 实际 HTTPS 域名、证书有效性、完整证书链、端口和反向代理；在后台配置 `request` 合法域名，涉及上传／下载时分别配置相应合法域名。域名和端口需按实际地址匹配，不能用公网 IP 或 localhost 作为正式请求地址。[微信支付文档中的网络配置](https://pay.wechatpay.cn/doc/v3/partner/4012088031)
- [ ] 准备微信开发者工具、至少一台真实手机和家庭成员测试账号；确认体验版的成员配置与数量限制，以后台为准。
- [ ] 准备隔离的测试环境或测试账号和可清理的测试数据。先核实生产数据库、票据及密钥备份，并完成恢复演练后再让真实家庭数据进入新客户端。
- [ ] 核对隐私保护指引及实际收集的数据、照片授权和第三方服务；按小程序后台要求填写，以最终功能为准。

## 5. 执行步骤与验收

### P0：技术验证和会话决策

1. 在 `app` 分支的 `apps/miniprogram` 建立最小工程，配置开发、测试、生产 API 地址；使用开发工具构建并导入，测试环境与生产环境不得混用。
2. 实现统一请求适配层：超时、错误码、登录失效、取消和重复提交处理；调用 `/api/v1/auth/csrf`、`/api/v1/auth/login`、`/api/v1/me`，并以测试数据完成一次受保护的写操作。
3. 现有网页使用同源 `fetch` 和 Cookie；服务端 HTTPS 会话 Cookie 为 `HttpOnly`、`Secure`、`SameSite=Lax`，写请求还校验 CSRF Cookie 与请求头。小程序不应假设具备浏览器同源和 Cookie 行为。先在 iOS、Android 真机验证网络 API 的 Cookie、CSRF、重启和退出行为。
4. 若现有机制无法满足，新增独立的小程序登录和 Bearer 会话入口，复用现有账号与授权逻辑；明确凭证存储、过期、撤销、退出、传输和日志脱敏。小程序凭证与浏览器 Cookie 是不同威胁模型，不能全局关闭现有 CSRF、权限或安全 Cookie。最终方案须通过安全评审和真机验证。
5. 验证共享契约能否编译，以及生产构建包体积；记录需要抽取的纯逻辑与不可复用的浏览器依赖。

**通过条件**：真实手机在合法域名校验开启时可登录、读取、写入、退出；重启、失效和错误处理可解释；现有网站登录及写入未回归。会话方案形成明确决策后进入 P1。

### P1：家庭试用版

1. 实现登录、首次改密和退出；为每人使用已有独立账号，不保存明文密码。
2. 实现个人／家庭空间切换；分别验证本人数据、家庭数据、非成员访问，以及家庭费用归属与现有网站一致。
3. 移植账本列表、搜索筛选、支出新增／编辑／删除、退款和恢复；金额、日期、分类和服务端校验保持一致，提交中禁止重复触发。
4. 移植待办和基本报表；验证个人／家庭统计口径、退款后结果及跨客户端同步。
5. 增加加载、空数据、断网、失败重试、会话过期和表单未保存提示；适配安全区域和常见屏幕尺寸。
6. 用隔离数据在微信开发者工具及 iOS、Android 真机验证；上传体验版，按后台规则邀请家人试用。

**通过条件**：两名不同账号完成新增、修改、退款、待办和报表全流程；小程序写入在网页可见，网页写入在小程序刷新后可见；越权访问被服务端拒绝；原网页回归通过。

### P2：补齐日常能力

1. 适配选图、`uploadFile` 和私有票据读取：复用服务端文件限制和授权，明确图片请求携带会话凭证的方式、临时文件清理及失效处理，避免公开长期可访问的票据 URL。
2. 移植固定费用规则、期次付款／跳过和站内提醒；使用已有 worker，不把提醒调度放在小程序前台。
3. 补齐报表趋势、筛选明细和设置；比对网页与小程序在相同条件下的结果。
4. 对弱网、上传中断、文件超限、会话失效、重复付款及并发操作做针对性验证。

**通过条件**：授权用户能上传和读取票据，其他用户不能访问；固定费用不会因重复操作重复入账；提醒和报表与网页一致。

### P3：按需扩展与发布

1. 家庭管理、管理员操作、访客分享、PushPlus、AI 和衣柜逐项确认价值、个人主体类目和技术限制后实施。AI 仍由用户主动触发，识别结果先确认再写入。
2. 体验版完成家庭试用后，确认类目、备案、隐私信息和审核材料；如需正式发布，按微信后台流程提交审核、处理反馈并发布。体验版可作为家庭试用手段，但其可用资格、期限和人数以后台规则为准；不把体验版视为正式发布。
3. 建立版本记录、监控、备份、恢复和回滚流程；发布前记录当前服务端与小程序版本，先验证向后兼容，再安排变更。

## 6. 服务端与安全改造检查

- [ ] 将认证方式与业务权限分离；小程序和网页共享账号、家庭成员关系及服务端授权，不能只靠前端隐藏入口。
- [ ] 登录失败、停用账号、改密、过期、退出和设备丢失时的会话撤销语义明确；不记录密码、会话凭证、Cookie、AppSecret 或票据内容。
- [ ] 保护密码输入、HTTPS 传输和错误提示；客户端本地存储只保存必要凭证，不保存明文密码。
- [ ] API、上传和图片访问均验证本人、家庭成员与非成员边界；对会话、上传、图片缓存及删除清理建立测试。
- [ ] 保持现有浏览器 CSRF 和 Cookie 安全策略；新增鉴权方式不能让浏览器请求绕过既有保护。
- [ ] 后端迁移先验证旧网页兼容；任何数据库迁移先备份、在隔离环境演练并准备恢复步骤。

## 9. 给接手 Agent 的执行入口

本节与第 1—8 节共同构成执行说明；冲突时以本节的范围、依赖与验收为准。本文授权开展本地代码实现和隔离测试；生产部署、发布及使用真实账号或真实数据应遵循项目权限和用户当时的明确授权。不要把本文的规划状态当作任何阶段已完成。

### 9.1 开始前必须做的事

1. 读取仓库根 `README.md`、`docs/家庭收支与待办软件-需求设计.md`、`docs/项目技术路线.md` 和本文件；涉及衣柜时另读 `docs/智能衣柜-开发计划.md`。检查工作树和仓库内适用的 `AGENTS.md`，保留既有未提交改动。

3. 执行前确认 P1 类目和限制；无法获取后台信息时可继续隔离环境中的工程验证，但不得宣称审核可通过或将有疑问的功能提交发布。小程序体验版、真机或后台操作缺少权限时，完成可独立进行的代码和验证，明确列出需要用户操作的步骤。
4. 默认从 P0 开始顺序执行；每个工作包独立记录结果，后继包不能以模拟验证冒充真机或生产验证。不要直接使用生产数据库做破坏性测试。

### 9.4 认证设计决策门槛

- 登录入口也受全局 CSRF guard 约束：需覆盖登录、改密后重新发放会话、退出、文件上传和图片读取，不能只验证 `GET /me`。
- 实际检验生产模式请求的 Origin、Cookie 收发及重启行为；在开发者工具关闭域名校验的结果不能作为正式环境证据。避免将客户端能伪造的 `Origin` 当作小程序身份凭据。
- 新方案若使用 bearer 令牌，只对明确声明、仅接受该凭证的认证路径及受保护请求设计独立验证：拒绝混用 Cookie 和 bearer 造成的绕过，维持浏览器 Cookie 路径的 Origin/CSRF 校验。小程序登录入口也需限制暴力尝试，服务端复用现有账号状态和权限检查；具体机制按测试和威胁模型确定，不预先认定某种实现安全。
- 测试覆盖登录失败、停用、首次改密、密码重置、凭证过期及撤销、退出、跨账号隔离、原浏览器写入与无 Origin 的浏览器 Cookie 请求被拒绝；检查日志脱敏。

### 9.5 常规验证和交接格式

每个工作包运行受影响的类型检查、单元／集成测试与构建；必要时运行仓库根 `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm test:integration`、`pnpm build` 和对应 E2E。真实设备、标准 PostgreSQL、线上部署与第三方服务的验证分别记录，不能用模拟结果替代。失败时记录命令、原因、影响、修复和复测；非相关既有失败单独说明。
