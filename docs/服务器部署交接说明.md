# 家常账服务器部署交接说明

本文是 HomeData 生产服务器的可执行部署手册。后续部署前先读取本文，再按步骤执行。不要重新试探 SSH 登录、要求用户重复输入密码、并行构建镜像或要求用户重启服务器。目标是将 GitHub 仓库 `https://github.com/Quarria/HomeData` 的 `origin/dev` 已提交代码部署到 Ubuntu 服务器；服务器不需要安装 Git。

## 服务器和持久数据

- SSH：`root@47.110.63.143:22`。本机已配置别名 `homedata-server` 和持久化密钥，连接不需要密码。
- 应用源码：`/home/homedata/app/current`；Compose 目录：`/home/homedata/app/current/deploy`；Compose 项目：`homedata`。
- PostgreSQL 数据：`/home/docker/postgres`；票据数据：`/home/docker/homedata/receipts`。
- Compose 环境文件：服务器上的 `deploy/.env` 和 `deploy/runtime.env`。它们包含真实凭证，不得覆盖、删除、下载到本地或提交到 Git。
- 网站入口：HTTP TCP 80，即 `http://47.110.63.143/`。外网无法访问时检查云厂商安全组 TCP 80 入站规则。

## SSH 连接（已经配置，无需用户操作）

本机私钥在 `%USERPROFILE%\.ssh\homedata-deploy-ed25519`，SSH 别名配置在 `%USERPROFILE%\.ssh\config`：

```sshconfig
Host homedata-server
  HostName 47.110.63.143
  User root
  Port 22
  IdentityFile C:\Users\yu429\.ssh\homedata-deploy-ed25519
  IdentitiesOnly yes
```

服务器 `/root/.ssh/authorized_keys` 已安装对应公钥。用户明确要求长期保留，以供后续免密码部署。私钥只留在本机 `.ssh` 目录；不要复制到仓库、发布包、GitHub、聊天或临时构建目录，也不要在部署后撤销公钥。

部署开始时在 Windows PowerShell 的仓库根目录无交互验证连接：

```powershell
ssh.exe -o BatchMode=yes homedata-server "printf 'SSH_OK '; hostname"
```

成功应输出 `SSH_OK` 和服务器主机名。后续所有 `ssh`、`scp` 命令都使用别名 `homedata-server`，不要再向用户索取 IP、端口或密码，也不要让用户切换终端手动输入密码。若此检查失败，查看 SSH 的具体错误、检查本机 SSH 配置与网络；不要回退密码登录，不要要求用户重启服务器。

## 部署前检查

1. 执行 `git fetch origin` 并确认成功；只部署 `origin/dev` 上已提交并推送的代码，不要把工作区未提交或未跟踪内容打进包。
2. 通过 SSH 检查服务器可登录、Docker 正常、磁盘有足够空间，且 `current/deploy/compose.yaml`、`.env`、`runtime.env` 存在。只检查环境文件是否存在，不要打印其内容。
3. 确认 PostgreSQL 和票据使用上文的 `/home/docker` 持久化路径。
4. 用下面的命令检查目标版本 `apps/server/prisma/migrations/` 是否比服务器当前源码新增迁移。发现新增迁移时，先按项目备份流程备份数据库再发布；若有迁移被目标版本删除则停止发布并先查清原因。
5. 严禁执行 `docker compose down -v`、删除持久化目录或重置生产数据库。

迁移目录自动比对（本机 PowerShell 执行；不读取环境变量文件）：

```powershell
$targetMigrationDirs = @(git ls-tree -r --name-only origin/dev -- apps/server/prisma/migrations | Where-Object { $_ -match '/migration\.sql$' } | ForEach-Object { ($_ -split '/')[-2] } | Sort-Object -Unique)
if ($LASTEXITCODE -ne 0) { throw '读取目标版本迁移列表失败，停止部署' }
$serverMigrationDirs = @(ssh.exe homedata-server "find /home/homedata/app/current/apps/server/prisma/migrations -mindepth 2 -maxdepth 2 -type f -name migration.sql -printf '%h\n' | sed 's#.*/##' | sort")
if ($LASTEXITCODE -ne 0) { throw '读取服务器迁移列表失败，停止部署' }
$newMigrations = @($targetMigrationDirs | Where-Object { $_ -notin $serverMigrationDirs })
$removedMigrations = @($serverMigrationDirs | Where-Object { $_ -notin $targetMigrationDirs })
if ($removedMigrations.Count -gt 0) { throw "目标版本移除了数据库迁移：$($removedMigrations -join ', ')；停止部署并调查" }
if ($newMigrations.Count -gt 0) { Write-Host "发布前必须备份数据库；新增迁移：$($newMigrations -join ', ')" }
```

## 本地打包并上传

在 Windows PowerShell 的仓库根目录执行。包名带提交短 ID，避免误传或覆盖其他发布包：

```powershell
$releaseId = (git rev-parse --short=12 origin/dev).Trim()
if ($releaseId -notmatch '^[0-9a-f]{12}$') { throw '无法确认 origin/dev 提交 ID，停止部署' }
$archive = Join-Path $env:TEMP "homedata-release-$releaseId.tar.gz"
git archive --format=tar.gz --output=$archive origin/dev
if ($LASTEXITCODE -ne 0) { throw 'git archive 失败，停止部署' }
scp.exe $archive "homedata-server:/home/homedata/app/homedata-release-$releaseId.tar.gz"
if ($LASTEXITCODE -ne 0) { throw '上传失败，停止部署' }
```

记录 `$releaseId`，后续远程命令中的 `$releaseId` 要使用这个值。`git archive` 只包括 Git 已跟踪且已提交的 `origin/dev` 文件，不包含未跟踪文件、`.git`、本机 SSH 密钥、`node_modules` 或服务器环境文件。上传失败就停止，不要继续解包或构建。

## 服务器预检与解包

在 PowerShell 里执行下面的命令；它会使用上一步得到的提交 ID：

```powershell
$remoteArchive = "/home/homedata/app/homedata-release-$releaseId.tar.gz"
$remoteCommand = "set -e; test -f /home/homedata/app/current/deploy/compose.yaml; test -f /home/homedata/app/current/deploy/.env; test -f /home/homedata/app/current/deploy/runtime.env; docker info >/dev/null; df -h /; cd /home/homedata/app/current; tar -xzf '$remoteArchive'; cd deploy; docker compose --env-file .env config --quiet"
ssh.exe homedata-server $remoteCommand
if ($LASTEXITCODE -ne 0) { throw '服务器预检或解包失败，停止部署' }
```

`config --quiet` 只验证 Compose 配置，不打印凭证。解包会覆盖同名文件，但不会自动删除旧版本已删除或改名的文件；如果本次删除或重命名源码，应改用干净的版本目录构建，避免旧文件残留进入镜像。不要覆盖或删除 `.env`、`runtime.env`。

## 分开构建镜像（关键：不可并行）

API 和 Web 镜像的 Dockerfile 将 workspace/package manifests 与源码分层复制：仅源码改变时，`pnpm install` 层保持命中；依赖定义变化时，BuildKit 的共享 `homedata-pnpm-store-v11` cache mount 复用已下载包，只下载新增或变更的依赖。首次使用此缓存需要下载依赖一次。服务器到 npm registry 的下载较慢。以前一次性 `docker compose up -d --build` 同时构建 API/Web，服务器一度失去响应，用户被迫重启。随后尝试 `docker compose --parallel 1 build`，但实际 BuildKit 仍同时启动两个服务的构建。**不要重复这两种方式，也不要因下载慢要求用户重启。不要清理 BuildKit 全部缓存，否则会同时删除 pnpm cache mount，导致下一次依赖安装重新下载。**

正确方式是：临时把 pnpm 网络并发限制为 4，用 `trap` 自动恢复 `pnpm-workspace.yaml`，一次只构建一个 Compose 服务。先运行 API 构建，等成功完成后再运行 Web 构建。构建过程中现有容器继续运行；只有两个镜像都成功后才应用新镜像。

API 单服务构建：

```powershell
ssh.exe homedata-server 'set -e; cd /home/homedata/app/current; backup=/tmp/homedata-pnpm-workspace.yaml.original; workspace=/home/homedata/app/current/pnpm-workspace.yaml; if test -e "$backup"; then echo DEPLOY_TEMP_BACKUP_EXISTS; exit 1; fi; cp "$workspace" "$backup"; restore_workspace() { if test -f "$backup"; then cp "$backup" "$workspace" && rm -f "$backup"; fi; }; trap restore_workspace EXIT; trap "exit 129" HUP; trap "exit 130" INT; trap "exit 143" TERM; printf "\nnetworkConcurrency: 4\n" >> "$workspace"; cd /home/homedata/app/current/deploy; docker compose --env-file .env build api; echo API_IMAGE_BUILD_OK'
```

必须等命令完成，看到 `API_IMAGE_BUILD_OK` 且退出码为 `0`，才能执行 Web 构建：

```powershell
ssh.exe homedata-server 'set -e; cd /home/homedata/app/current; backup=/tmp/homedata-pnpm-workspace.yaml.original; workspace=/home/homedata/app/current/pnpm-workspace.yaml; if test -e "$backup"; then echo DEPLOY_TEMP_BACKUP_EXISTS; exit 1; fi; cp "$workspace" "$backup"; restore_workspace() { if test -f "$backup"; then cp "$backup" "$workspace" && rm -f "$backup"; fi; }; trap restore_workspace EXIT; trap "exit 129" HUP; trap "exit 130" INT; trap "exit 143" TERM; printf "\nnetworkConcurrency: 4\n" >> "$workspace"; cd /home/homedata/app/current/deploy; docker compose --env-file .env build web; echo WEB_IMAGE_BUILD_OK'
```

同样等待 `WEB_IMAGE_BUILD_OK` 且退出码为 `0`。若构建失败，保留现场和日志；先检查临时备份是否已由 trap 清除、`pnpm-workspace.yaml` 是否已恢复（不应有本次追加的 `networkConcurrency: 4`），再判断原因。不要启动另一项并行构建，不要执行 `up -d`。依赖下载慢但持续有进度时继续等待，不要中断或重启服务器。

## 应用镜像和验收

只有 API 和 Web 都成功构建后，才应用镜像。命令不能带 `--build`：

```powershell
ssh.exe homedata-server 'set -e; cd /home/homedata/app/current/deploy; docker compose --env-file .env up -d'
```

该命令会重建应用容器，不会重启 Ubuntu 服务器或删除数据库/票据数据。Compose 会先等待数据库健康、运行 Prisma 迁移，再启动 API 和 worker。`migrate` 显示 `Exited (0)` 是正常状态。

服务端检查：

```powershell
ssh.exe homedata-server 'set -e; cd /home/homedata/app/current/deploy; docker compose --env-file .env ps -a; printf "LOCAL_HTTP "; curl --max-time 10 -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1/; printf "API "; docker inspect --format "{{.State.Status}}" homedata-api-1; printf "WORKER "; docker inspect --format "{{.State.Status}}" homedata-worker-1; printf "WEB "; docker inspect --format "{{.State.Status}}" homedata-web-1'
```

预期：`db` 为 `healthy`，`api`、`worker`、`web` 正在运行，`migrate` 为 `Exited (0)`，本机 HTTP 为 `200`。再从本机验证公网入口：

```powershell
curl.exe --noproxy "*" --max-time 15 -sS -o NUL -w "HTTP %{http_code}\n" http://47.110.63.143/
```

预期为 `HTTP 200`。如异常，查看 `docker compose --env-file .env ps -a` 和相关容器最近日志，不要打印环境变量文件或将凭证、日志、密钥提交到 GitHub。成功后删除发布包，保留 SSH 私钥与服务器授权公钥：

```powershell
Remove-Item -LiteralPath $archive
ssh.exe homedata-server "rm -f -- '$remoteArchive'"
if ($LASTEXITCODE -ne 0) { Write-Warning '服务器发布压缩包未清理；可稍后仅删除该提交 ID 对应的文件' }
```

## 遇到停顿或失败时

- 以前本机临时 PowerShell 脚本曾被 Execution Policy 拒绝，PSReadLine 也出现历史文件访问错误。这些与服务器无关。不要再生成临时 `.ps1` 绕过交互；直接通过 `ssh.exe homedata-server` 和 `scp.exe` 调用 SSH。
- SSH 输出末尾曾出现 `close - IO is still pending on closed socket`，但远端成功标记已输出且本地退出码为 `0`。这种情况下先按验收命令检查实际状态，不要立即重跑部署。
- 构建耗时长、输出间歇停顿时，先继续读取当前 SSH 会话输出。确认命令已经失败后再新建只读 SSH 检查。不要让用户按 Ctrl+C，不要重启整台服务器，不要重启 Docker 守护进程。
- 构建失败时现有容器仍使用旧镜像；保留它们，确认临时配置还原后再分析。迁移失败时不要继续强行启动 API/worker，应先判断是否需要恢复数据库备份。
- **已知问题（提交 `e035398` 起）**：Prisma 配置在 `migrate deploy` 后运行 `tsx prisma/seed.ts`；但运行镜像没有 `/app/apps/server/node_modules/.bin/tsx`，因此会先报告 `No pending migrations to apply`，随后因 `spawn tsx ENOENT` 以退出码 1 结束。此时数据库迁移本身可能已成功，不能误认为迁移执行失败或重跑服务器。先确认迁移日志及无待执行迁移；分类 seed 使用按 `code` 的幂等 upsert，可用下列命令补跑：

  ```bash
  cd /home/homedata/app/current/deploy
  docker compose --env-file .env run --rm --no-deps --entrypoint sh migrate -c 'cp prisma/seed.ts dist/prisma/seed.ts && node --experimental-strip-types dist/prisma/seed.ts'
  ```

  seed 成功后，用 `docker compose --env-file .env up -d --no-deps api worker web` 启动应用服务。注意这只是应急恢复：Compose 的 migrate 容器仍会显示失败。**持久修复应在 `deploy/Dockerfile.server` 运行阶段复制 `/app/apps/server/node_modules`，确保 seed 命令 `tsx` 可用；修复需提交并推送到 `dev` 后，后续部署才能按正常依赖流程通过 migrate。** 在持久修复进入 `origin/dev` 前，部署新版本时要预期 `up -d` 在 seed 步骤失败，并按本段处理。
- 容器正常但外网不通，检查云安全组 TCP 80 和服务器防火墙，不要因此修改数据库配置或重启服务器。
- 严禁 `docker compose down -v`、删除 `/home/docker/postgres` 或 `/home/docker/homedata/receipts`、重置生产数据库。
