# 智能衣柜需求与实施方案

版本：v1.0（功能已确认，进入开发计划阶段）
日期：2026-10-20
适用系统：家常账 HomeData；两人家庭；2 核 2 GB 服务器。

## 1. 目标与范围基线

帮助家庭成员方便地录入、查找和搭配已有衣物，并按需关联购买账目与养护待办。优先减少录入负担、避免找不到衣服、提供本地日常及目的地旅行期间天气与场景合适的库存搭配。

已确认的方向：沿用现有技术栈，在家常账内部新增衣柜功能；复用现有权限、数据库和 worker；AI 使用外部 API；不部署本地推理模型；控制项目复杂度。虚拟试穿、星座等附加能力不进入本次范围。

本文区分三类内容：

- **范围基线**：本次计划交付的产品能力与业务边界。
- **实现建议**：可以由开发按现有代码调整的技术细节，不要求逐项由使用者选择。
- **已确认选择**：影响使用方式和外部服务使用的产品决定，列在第 9 节；后续实施以这些决定为准。

自动抠图首版暂缓，不作为衣物识别和搭配的前置条件。目的地旅行穿衣推荐纳入本次范围，复用天气与搭配能力，不另建旅行管理系统。

### 2.1 录入字段

| 字段               | 要求              | 说明                                                                                                                             |
| ------------------ | ----------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 照片               | 首版每件 1 张主图 | 后续允许替换；不做多图管理和批量导入                                                                                             |
| 名称               | 必填              | 可以采用 AI 建议或按类别生成默认名称，用户可改                                                                                   |
| 类别               | 必填              | 上装、外套、下装、连衣裙／连体、鞋、配饰                                                                                         |
| 所有人             | 必填              | 默认本人；创建时可选择同一有效家庭内的另一有效账号，衣物直接归入该成员衣柜；不开放任意账号代录或创建后的随意转移                 |
| 可见范围           | 固定              | 衣物只对所有人本人可见，不提供家庭共享选项                                                                                       |
| 主色               | 可选              | 支持未知，不因 AI 识别失败阻断保存                                                                                               |
| 适用季节           | 可选、多选        | 春／夏／秋／冬四个独立选项，可任意组合；全选显示“四季”，空数组显示“待补充”，不存“春秋”这类单选枚举，不因缺失推断需要购买同类衣物 |
| 场景               | 可选、多选        | 通勤、休闲、运动；以后可增加，无需自由标签体系                                                                                   |
| AI 穿搭建议        | 可选，最多 80 字  | 随衣物识别请求生成的简短场景／搭配方向建议；用户可编辑；后续推荐只将候选衣物的该字段作为参考，不作为硬性规则                     |
| 状态               | 必填              | 可穿／清洗中／已收纳／已退役，新增默认可穿                                                                                       |
| 收纳位置           | 可选              | 普通短文本，如“主卧衣柜左侧”，不建设柜格层级管理                                                                                 |
| 备注               | 可选              | 补充尺码、品牌、洗护说明等，首版不拆成大量字段                                                                                   |
| 添置日期           | 可选              | 独立记录获得这件衣物的日期；新购默认今天，关联账单时可按账单日期预填，旧衣不记得时允许留空；不等同于系统录入时间                 |
| 关联支出／本次支出 | 按录入方式填写    | 同时记账时填金额与消费日期；关联已有账单不重复创建支出；礼物、旧衣可无账单                                                       |
| 适用层次           | 可选、多选        | 内搭／中层／外层；AI 可建议，人工可改；首版搭配先做内搭＋外层两层，三层组合后置                                                  |

AI 的季节和保暖建议是推测；洗护说明以实物洗标或人工输入为准。

### 2.2 推荐规则

先用确定性规则保证可用，再按需让 AI 优化搭配或理由：

1. 只读取当前账号拥有的衣物，筛选可穿状态；家庭成员衣物不跨账号展示或自动混搭。
2. 根据目的地实际温度、雨天、适用层次和场景筛选；季节为多选参考标签，按包含关系匹配，不把一件衣物永久限制在单一季节，也不能仅凭当前月份排除温度合适的衣物。季节缺失的衣物允许手动选用，自动推荐需标识信息不足。
3. 按完整结构产生少量候选：“上装＋下装＋鞋”或“连衣裙／连体＋鞋”；低温时按适用层次组合内搭＋外层，配饰可省略。不能用外套替代内搭，或仅靠衣物类别推断可以叠穿；三层组合首版暂缓。
4. 按颜色兼容、场景、天气评分，避免只取每类别最高分后直接拼成一套。
5. 默认给最多 3 套；库存不足时少给或说明缺少必要品类，不虚构衣物、不直接建议购物。
6. 如调用 AI，只提供少量候选的 ID 与标签；服务端检查返回 ID、所属人、状态和组合结构，不合法时回退规则结果。
7. 收藏后再次展示时检查已删除／退役／不可穿单品并提示，不能继续显示为可直接穿用的完整套装。

不引入穿着历史时，系统只能减少同次候选重复，不能声称已经实现“避免最近穿过”。

### 2.3 目的地旅行穿衣推荐

在“搭配”内增加“日常／旅行”切换。日常使用家庭默认城市；旅行使用本次输入的目的地，不修改家庭默认城市。

| 输入     | 规则                                                                                   |
| -------- | -------------------------------------------------------------------------------------- |
| 目的地   | 输入城市或区县，搜索后选择明确结果；展示国家／省市区，避免同名城市误选；首版一个目的地 |
| 出发日期 | 必填，默认今天；可以选择未来日期，按目的地当地日期划分旅行日                           |
| 旅行天数 | 必填正整数，以天为单位；建议首版支持 1—30 天，作为可调整的实现限值                     |
| 场景     | 可选，默认休闲；首版整段旅行使用同一场景，可选通勤／休闲／运动                         |

结束日期 = 出发日期 + 旅行天数 − 1。例如出发日 11 月 3 日、旅行 3 天，范围为 11 月 3—5 日，出发日计第 1 天。

目的地与日期有效后自动查询天气；用户点击一次“生成旅行穿搭”后，把逐日天气、场景、可选穿搭想法及候选组合合并为一次 AI 请求，再从规则候选中选择并说明理由。不会逐日多次调用模型。

结果包含：

- 目的地、旅行日期、天气获取时间和当前可预报的日期范围。
- 逐日天气摘要：最低／最高温、体感温度范围（供应商提供时）、天气现象、降雨概率及必要风力信息；缺失字段不编造。
- 每日一套主推荐，显示具体衣物照片、名称和简短理由；相近天气允许复用鞋、外套和整套搭配，不按每天都穿全新一套推高衣物需求。
- 低温、温差和雨天的穿衣提示；只能据标签建议防风／防雨，不把普通外套或鞋虚构为有专业防护性能。
- 对库存不足、属性不全、天气暂不可用和远期无预报分别说明；可保存其中某天的搭配到现有收藏。

推荐依据是生成时的衣柜状态，不保证出发当天仍然可穿；后续重新生成或保存时重新校验。首版不自动安排洗衣、不推断旅行中的清洗条件，也不建设多目的地路线、打包数量优化、旅行日程或自动提醒。

### 2.4 旅行天气的边界

天气服务只能提供有限时间范围内的预报，旅行天数不等于可预报天数。Open-Meteo 官方说明默认提供 7 天、可请求最多 16 天；上线实现应以实际响应日期和数据完整性为准，不硬编码认为未来任意日期均有天气。[官方预报文档](https://open-meteo.com/en/docs)

| 覆盖情况             | 产品行为                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| 旅行全部在预报范围内 | 按逐日预报生成穿衣推荐，标明获取时间，远期预报提示可能变化                                         |
| 只覆盖旅行的一部分   | 有预报的日期正常推荐；其余逐日标识“尚无天气预报”，不延用前一天温度假装有数据                       |
| 全部超出预报范围     | 保留目的地与日期输入，说明临近出行再生成；允许用户手选冷热／雨天后生成明确标注为手动条件的参考搭配 |
| 外部查询失败         | 如有旧数据，显示数据时间与状态；无数据时允许手选天气，不用家庭城市或模拟天气替代目的地天气         |

无预报日期只有在用户明确提供天气条件时才提供对应参考搭配；不由 AI 猜测逐日气温。首版不接历史气候／季节预测等第二种天气服务，不自动定时刷新并调用 AI。

## 4. 技术路线

| 层次   | 本次方案                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------ |
| 前端   | 现有 Vue 3／TypeScript；新增衣物列表、编辑、详情、搭配视图，复用现有视觉和表单组件                                 |
| 契约   | 在 `packages/contracts` 增加 Zod 请求和响应定义                                                                    |
| 后端   | 在 NestJS 增加 `wardrobe` 模块；复用会话、家庭成员校验与审计惯例                                                   |
| 数据库 | 继续 PostgreSQL＋Prisma，通过新增迁移扩展                                                                          |
| 图片   | 服务器私有持久化目录，主图＋缩略图；受鉴权接口读取，不挂公开静态目录                                               |
| AI     | 优先现有 DeepSeek；只有效果或可用性不达标时再决定是否增加通义适配                                                  |
| 天气   | 优先 Open-Meteo 地点搜索与预报，使用一个供应商体系；家庭默认城市＋单次旅行目的地，共享缓存，不做自动定位／多源解析 |
| 任务   | 现有数据库 AI 任务队列和 worker，并发先设为 1                                                                      |
| 部署   | 复用现有 Compose 服务；优先本机／CI 构建，遵守现有串行构建约束                                                     |

衣柜规模小，不新增缓存中间件。天气数据可用 PostgreSQL 中少量缓存记录；重启后缓存可重建。

### 4.1 数据结构建议

| 数据            | 最小职责                                                                                                                                                                                                                                             |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Garment`       | ownerId（所有人）、createdById（录入人）、本人可见、名称与标签、最多 80 字 stylingAdvice、seasons 季节枚举数组（0—4项，去重）、适用层次、状态、位置、图片引用、acquiredOn（添置日期）和可选支出 ID、版本、软删除标记；不保存重复的“是否代买”布尔字段 |
| `WardrobeImage` | 上传者、私有主图／缩略图存储键、哈希、格式、大小、尺寸、创建时间；支持清理未关联图片                                                                                                                                                                 |
| `Outfit`        | 所有人、名称、场景、说明、可选天气快照、创建更新时间                                                                                                                                                                                                 |
| `OutfitItem`    | 套装与衣物关联、位置／角色；保存时检查权限、数量和组合结构                                                                                                                                                                                           |
| 现有 `AiRun`    | 复用衣物识别与穿搭推荐任务类型；推荐输入包含用户想法、天气／场景和规则候选，旅行整段只创建一次任务                                                                                                                                                   |
| 天气缓存        | 城市坐标、目的地时区、预报日期范围、天气数据、获取时间与过期时间；少量记录即可                                                                                                                                                                       |

一件衣物首版最多关联一笔支出，一笔支出可以被多件衣物引用。未关联不影响使用。首版没有单件成本计算，避免整单金额重复累计。

草稿字段主要保留在录入表单；上传图片和 AI 任务可在页面离开后继续完成。首版不做跨设备完整草稿箱。未关联图片通过定时任务清理，实现时设置合理保留时间并避开执行中的 AI 任务。

旅行参数、候选快照和最终推荐复用 `AiRun` 输入／结果；天气缓存仍复用现有数据层。首版不新增 Trip、行程、旅伴、行李等表，也不提供完整旅行历史管理。

### 4.2 接口组织建议

统一在现有 `/api/v1` 下增加衣柜资源，不另开 API 服务。

- `POST /wardrobe/images`、`GET /wardrobe/images/:id`：上传和鉴权读图；缩略图使用同一资源的规格参数。
- `GET/POST /wardrobe/garments`、`GET/PATCH/DELETE /wardrobe/garments/:id`：衣物管理；创建输入包含 ownerId、acquiredOn 和 discriminated union 形式的 expenseMode=NEW/EXISTING/NONE，NEW 携带受限支出字段，EXISTING 只传现有支出 ID。衣物＋新支出在一个后端事务和幂等操作中完成。
- `GET/POST /wardrobe/outfits`、`GET/PATCH/DELETE /wardrobe/outfits/:id`：套装管理。
- `POST /ai/garment-extractions`：用户主动创建衣物识别异步任务，复用现有任务状态查询。
- `POST /ai/wardrobe-recommendations`：日常或旅行用户主动创建一次穿搭推荐任务；候选由库存规则先行生成，模型只能筛选已有候选并说明理由，输出再由服务端校验。
- `GET /wardrobe/locations?query=...`：目的地搜索，返回结构化地点标识、行政区、坐标和时区；输入防抖、按词缓存，不由 AI 解析地点。
- `GET /wardrobe/weather`：按明确目的地和日期范围读取／刷新天气缓存，不调用生成模型；后端校验坐标、日期和天数范围，不接受任意上游 URL。

接口名为实现建议；新增操作遵循现有权限、版本冲突、幂等和错误格式。AI 请求使用 POST，避免页面预取或链接访问意外触发付费任务。

## 5. 关键流程与联动规则

### 5.1 录入

选择单品照片 → 客户端压缩／预览 → 上传至私有图片目录 → 手填或主动识别 → 展示可编辑草稿 → 用户确认 → 保存衣物。

识别失败保留图片和手工输入；AI 结果不自动覆盖用户刚修改的字段。图片不抠图也能识别，识别和抠图必须相互独立。

图片建议长边约 1024 像素、目标体积 100—300 KB；客户端压缩不替代后端验证。后端需限制真实格式、文件体积与解码像素总量，去除 EXIF，以单张处理控制峰值。精确限值作为实现参数，不要求使用者决定。

### 5.2 推荐

选择场景和穿搭想法 → 读取天气或手选天气 → 获取本人可穿衣物 → 规则构造有限候选 → 点击生成后将候选及必要上下文提交 AI → 服务端只接受候选 ID 并再次校验 → 展示图片与推荐理由 → 用户可保存套装。AI 无权创造库存外衣物，失败、未配置或额度耗尽时回退规则推荐。

缓存至少区分账号、场景、天气区间与衣柜版本。衣物更新使相关缓存失效，保存套装前再次鉴权与检查状态。打开列表、首页或刷新天气均不自动创建付费任务。

### 5.2.1 旅行推荐的实现流程

输入并选择目的地 → 输入出发日期和旅行天数 → 后端计算包含首尾的日期范围 → 按目的地时区查询逐日预报并标记覆盖情况 → 用户触发生成 → 按逐日天气从本人库存构造有限候选 → 将整段旅行一次发送给 AI 选择并说明理由 → 服务端逐日验证候选 ID 并展示。不得按天创建多个模型调用。

- 地点使用地理编码 API，不用大模型识别城市；同名结果让用户选择。官方接口提供地点搜索与时区信息：[Open-Meteo 地点搜索](https://open-meteo.com/en/docs/geocoding-api)。
- 天气按坐标、日期范围和时区缓存约 30—60 分钟；地点搜索结果可更长时间缓存。同一目的地的天气缓存可跨家庭成员复用，个人推荐结果不可跨账号复用。
- 能一次取得的多日天气不逐日发请求；只获取推荐需要的逐日字段，不下载整段逐小时数据。
- 对相似天气可复用规则组合，再映射到日期；用户主动重新生成时重新计算并创建一个推荐任务。
- 只向模型发送有限候选所需的衣物属性、穿搭想法、场景及必要的逐日天气；不发送衣物原图、其他家庭成员衣物或账本信息。
- 一次旅行生成最多调用模型一次，占用一次推荐额度；天气查询和纯规则计算不消耗 AI 次数。
- 推荐缓存额外包含目的地、目的地时区、出发日、天数与逐日天气版本；修改目的地或日期不得复用旧行程结果。

### 5.3 衣物与账目一次录入

添加衣物的表单提供三种方式，普通用户只完成一张表单和一次最终确认：

| 方式         | 用户填写                                                                     | 保存结果                                   |
| ------------ | ---------------------------------------------------------------------------- | ------------------------------------------ |
| 本次同时记账 | 衣物信息、所有人、添置日期、支出金额、消费日期；支出名称默认跟随衣物名，可改 | 一笔服饰支出＋一件衣物＋二者关联，一次提交 |
| 关联已有账单 | 选择本人有权关联的现有支出，其余字段预填或补充                               | 仅新增衣物并关联原支出，不再创建或复制账单 |
| 不关联账单   | 衣物信息，可选添置日期                                                       | 仅建衣物档案，适用于旧衣、礼物或无凭证情形 |

普通添加默认“不关联账单”，避免把旧衣误记成新支出；新购时主动选择“本次同时记账”。本次记账默认分类为服饰、付款人为当前账号、费用归属为个人支出；不因选择另一衣物所有人而自动改为家庭支出。从家庭账本进入时，保留原家庭费用归属规则与明确可见性确认。

反向入口也不重复录入：已有服饰支出提供“添加衣物”，固定使用该支出 ID，自动进入关联方式并预填日期与名称。识别到的票据已有支出草稿时，复用该草稿里的金额和日期；用户在同一录入流程补衣物信息后统一确认，不能先保存一笔再在衣柜重复记一笔。单品照片与票据照片是不同资源，不能把衣物照自动当成票据凭证。

一张订单买多件衣物时，可在同一账单入口逐件补衣物，每件可以选择不同所有人；每件只有自己的照片和属性，所有衣物复用同一笔支出。不要求一次做复杂批量上传，后续“再添加一件”直接带同一个支出 ID，不重复填总金额，也不自动给每件复制订单总价。

**后端实施：**当前 LedgerService.create 已将付款人固定为调用者，且在幂等事务中创建支出。新增统一入口应提取可在同一个 Prisma tx 内调用的记账领域方法，复用既有金额、分类、归属、审计和权限规则，再创建衣物与关联；不能让前端先调记账再调衣物拼成两个独立成功步骤，也不能在外层事务内调用开启另一事务的原方法冒充原子提交。

图片上传与 AI 识别先行，不占用数据库事务。最终保存时才在短事务中校验图片归属、目标成员资格、账单权限，创建支出／关联、衣物与审计；失败全回滚，保留表单和已上传图片以便重试。网络超时后用相同幂等键查询／重试，不能产生重复支出或重复衣物。

已有账单只能由付款人或既有规则允许的主体建立关联；“看得到”不自动等于能把他人的账目绑定到任意衣物。衣物删除不删账目，账目删除／退款不自动删衣物；原购买者管理财务，衣物所有人管理实物状态。

### 5.3.1 替家庭成员购买

“这件衣服给谁”默认“自己”，选择另一家庭成员即表示替对方购买，无需再维护一个可能矛盾的“是否代买”复选框。

例如 A 买一件 299 元的外套送给 B：

- 最终确认一次，服饰支出仍由 A 付款，默认留在 A 的个人账本。
- 衣物 ownerId=B，createdById=A，直接进入 B 的个人衣柜；B 不再录一次衣物，也不会新增一笔支出。
- B 取得衣物、图片及后续编辑／删除／穿搭权；A 因为付款或录入，不自动获得 B 的私人衣柜持续访问权。
- 为对方录入时固定仅收衣人可见；不允许购买者替对方开放衣柜。
- 支出仍按原权限处理。B 可看到衣物和添置日期，但不能由关联 ID 读取 A 的私人金额、票据或账目明细；创建响应与错误也不得泄露这些字段。
- 定向创建权限只允许同一有效家庭内的有效账号，保存事务时重新检查成员关系；离开家庭或账号停用时拒绝代录，保留输入。首版不支持向未注册／家庭外的人投送衣柜。

本次明确允许的是“为同家庭成员购买时创建衣物”，不是共同编辑彼此已有衣物。所有权创建后不通过普通编辑表单随意转给别人。购买者的支出详情可保留“已为该成员建立衣物”的业务关联信息，不借此提供读取对方私有图片的通道。

### 5.3.2 添置日期、消费日期和录入时间

- 添置日期 acquiredOn：实际获得衣物的日期，可人工改；旧衣不确定时留空，不以今天伪造。
- 消费日期 occurredOn：账本记录付款／消费的日期，遵循现有账目规则。
- 系统录入时间 createdAt：系统自动生成，表示何时建档。

新购通常三者接近，但网购付款日、到货日和补录日可能不同。关联账单时只预填添置日期，用户改添置日期不能反向修改消费日期；修改衣物名称也不自动改账目名称和金额。

### 5.4 待办与家庭

衣物详情打开现有新增待办表单，带上标题、衣物名称和稳定引用；用户填写截止日、负责人并保存。首版不增加待办自动同步衣物状态的规则，也不把养护任务塞进固定费用模块。

衣物仅由所有人本人查看、编辑、删除及发起 AI 识别。为家庭成员代购时，衣物直接归收衣人并出现在其衣柜；购买人只在自己的账本记录支出，不因此获得对方衣柜的访问权。

## 6. AI 和服务器约束

### 6.1 AI 接入与费用控制

- 首版只复用现有 DeepSeek 能力和服务端凭证；日常／旅行推荐在用户点击时才调用文本模型，不为衣柜建设多供应商管理平台。
- 现有 `AiRunType` 只有票据与报表，需要明确增加处理分支；当前“票据，否则报表”的分派不能直接沿用到新增任务。
- 衣物识别与穿搭推荐使用独立限额桶，不挤占已有票据／报表额度；建议每人每日识别 10 次、推荐 5 次。日常和整段旅行推荐共用推荐桶。
- 默认关闭长思考，限制候选数量和输出长度；最多自动重试一次。相同请求幂等、相同用户重复图片识别尽量复用。
- 家庭月费用先以 10 元作为建议控制目标。首版用每日次数限制、有限重试和供应商可用的费用提醒控制，不建设精确月度预结算系统；该目标不构成绝对扣费上限。若必须严格达到金额即停，应单独增加调用前费用预留与累计控制。
- 失败释放应用额度不等于供应商不收费。记录上游用量，真实费用以上游账单为准。
- 使用 API 时仅发送必要单品图或标签，不发送整柜图片、完整账本和真人照片；凭证留在服务端。
- 使用者可在日常／旅行表单填写穿搭想法，点击生成时与天气、场景及候选衣物属性一同发送给模型。用户后续提供的提示词作为风格参考，不可覆盖库存、权限及天气事实；模型输出必须回指候选 ID，由服务端校验。
- 旅行推荐只发起一次聚合模型调用，不按天调用；地点解析和天气查询仍不由模型承担。

当前 DeepSeek 官方资料明确支持 `deepseek-flash` 图片输入，实际衣物准确率、延迟和账号可用性仍需验证：[官方视觉接口](https://api-docs.deepseek.com/guides/vision/)。

### 6.2 资源约束

- 不新增常驻模型或容器服务，不采用本地抠图兜底。
- 图片在数据库外保存，列表只加载缩略图并分页；单次上传和处理图片数量为 1。
- 主图替换、软删除和未完成录入均需有文件清理策略；被有效衣物引用的图片不能误清理。
- 新图片目录同时挂载给有读取需要的 API／worker，纳入备份与恢复演练。
- 对现有记账、提醒与报表做回归；检查上传、AI 等待、备份时的资源峰值。没有实测前不承诺精确新增内存。

## 7. 自动抠图 API 的费用与取舍

### 7.1 查到的公开标价

截至本次核查，阿里云公开计费页给出的低调用量档位如下。**该页面标题已标注“文档停止维护”，下表用于判断量级；实际可开通性和价格在决定接入时以控制台／购买页为准。**

| 能力               | 公开标价                              | 100 张一次处理的估算 | 适用判断                                           |
| ------------------ | ------------------------------------- | -------------------- | -------------------------------------------------- |
| 通用分割／商品分割 | 0.002 元／次，月调用量不超过 1 万次   | 0.20 元              | 可先对平铺／悬挂单品做样本验证                     |
| 通用高清分割       | 0.007 元／次                          | 0.70 元              | 只有普通分割效果不足时再评估                       |
| 服饰分割           | 0.008 元／次，月调用量不超过 100 万次 | 0.80 元              | 不能仅凭名称判断更适合单品照，需对照输入要求与效果 |

来源：[阿里云分割抠图计费页](https://help.aliyun.com/zh/viapi/product-overview/billing-is-introduced-1)。估算仅含调用费，不含重试和可能的存储／流量费用，不代表效果承诺。

免费额度方面：历史公告出现过首次资源包 0 元试用，但不能据此认定当前账号可领取或长期每月免费。通用／商品分割原有 2 QPS 免费活动已在 2023 年转为按量付费；免费 QPS、免费调用次数和免费资源包也不是同一含义。来源：[调价公告](https://help.aliyun.com/zh/viapi/product-overview/announcement-on-pricing-and-price-adjustment-of-commercial-products-in-1)。

只有实际选择接入时，再核对账户资格、额度、有效期、适用 API 与超额规则。免费资源耗尽后是否按量扣费，以领取条款为准；不把免费权益作为系统可用性的基础。

### 7.2 接入成本与本次建议

少量衣服的抠图调用费通常不是主要问题。额外工作主要包括服务开通、鉴权与 SDK、图片输入方式、获取并保存处理结果、失败降级和图片生命周期。

例如商品分割接口使用 ImageURL，推荐上海 OSS 链接；本地或其他来源文件需要按官方方式处理。结果 URL 有效期为 30 分钟，不能直接当成衣物的长期图片地址；要及时保存回本系统私有存储。接入不应因此将衣柜原图长期公开。来源：[商品分割接口文档](https://help.aliyun.com/zh/viapi/developer-reference/api-i8iw3k)。

**已确认首版暂缓抠图，理由是减少接口链路，而不是调用费高。** 先用干净背景拍照、上传前预览／裁剪。后续发现实际影响录入或搭配展示，再添加“手动抠图”按钮：对已存在图片异步处理一次，用户确认后采用，失败继续用原图。首版只需保持图片处理与业务解耦，不预建抠图供应商接口层。

| B 辅助录入       | 衣物识别任务、可编辑草稿、限额与失败回退                                        | 失败可手填；确认才入柜；重复请求不重复创建任务；不覆盖手改字段；已有票据识别不受影响                                                         |
| C 搭配与旅行     | 本地／目的地天气、手选天气、手动搭配、规则候选＋AI 推荐、套装收藏、旅行逐日穿衣 | 不虚构衣物、不混所有人；支持连衣裙与外套；出发日和天数计算正确；同名城市确认、目的地时区、部分／无预报、失败回退正确；刷新不自动触发模型调用 |

A—D 是同一范围内的实施顺序，不代表必须做四次生产发布。推荐内部逐批验收，完整核心流程稳定后再对家庭使用开放。

### 8.1 必要检查

- 契约、类型检查、构建和现有必要回归。
- 两账号／同家庭／离开家庭三类权限场景，以及直接请求图片和关联支出接口的越权检查。
- 任务重试、超时、重复提交、删除或替换图片后的竞态，以及 AI 不合法 ID 回退。
- 联合保存失败回滚、超时后幂等重试、已有账单多衣物不重复记账；代买时目标成员失效、图片权限转归、购买者不越权读对方衣柜、收衣人不越权读私人账单；添置日期独立修改不影响财务日期。
- 约 20 张自家单品照片的小样本，记录类别／颜色纠错率、耗时、失败率和实际用量；若不能明显减少手填工作，保留手工路径并调整模型，不盲目扩大 AI 范围。
- 目标服务器空闲、上传、识别、推荐与备份资源观测；不以本机测试替代 2 GB 环境验收。
- 旅行验收：出发日计入天数；跨月／跨年、目的地与服务器时区不同、30 天行程、预报部分覆盖与完全无覆盖均正确；缺失天气不冒充已知天气；改目的地／日期使旧结果失效；一次旅行只发一个汇总模型任务。

| D4   | AI 路线        | 复用现有 DeepSeek；用户点击才调用，失败可手工继续                                                          |
| D5   | 默认天气地点   | 一个家庭默认城市、设置可改，不自动定位；旅行目的地独立输入，不覆盖默认城市                                 |
| D6   | 费用控制       | 每人每日识别 10 次、日常与整段旅行 AI 推荐共用 5 次；复用现有供应商，不增加供应商                          |
| D7   | 目的地旅行穿衣 | 输入目的地、出发日期和旅行天数，自动查询逐日天气；一次 AI 请求结合库存候选按天推荐，不建设旅行管理系统     |
| D8   | 统一购衣录入   | 衣物与新支出一次提交，已有账单直接复用；增加添置日期；为同家庭成员购买时衣物直接归对方，付款记录仍归付款人 |
| D9   | 穿搭想法参考   | 使用者后续提供偏好例子，作为服务端推荐提示词的参考；不阻塞首版，不新增提示词编辑后台                       |
| D10  | 季节与叠穿     | 春／夏／秋／冬独立多选；结合实际温度和适用层次推荐，首版内搭＋外层，三层组合暂缓                           |
| D11  | 页面与样式     | 当前页面布局可作为开发基线，沿用现有生活日历设计，不再发散视觉方向                                         |

其余产品默认：每件一张照片、允许为同家庭成员购买时定向录入、本人库存推荐、日常最多三套／旅行每日一套主推荐、收藏搭配不算穿着、账目与待办都由用户确认。

## 10. 开工前和上线前需解决的工程问题

| 问题                 | 处理方式                                                                             | 解决时点  |
| -------------------- | ------------------------------------------------------------------------------------ | --------- |
| 现有 AI 真实可用性   | 使用现有配置发起少量样本请求，验证图片输入和结构化结果；不输出密钥                   | 批次 B 前 |
| API 任务类型扩展     | 明确分派新任务、独立额度和权限检查，保持旧功能兼容                                   | 批次 B    |
| 私有图片和清理       | 定义上传归属、访问权限、替换／删除、未关联图片清理以及处理中的引用保护               | 批次 A    |
| 城市搜索和天气可达性 | 验证服务器能访问地理编码／预报服务，保存坐标与时区，定义旧数据／不可用及预报覆盖状态 | 批次 C 前 |
| 旧共享数据清理       | 迁移时撤销原家庭共享记录，将衣物设为仅所有人可见                                     | A—C       |
| 数据迁移与备份       | 新增表迁移、私有目录挂载、数据与文件同步备份，验证恢复                               | 上线前    |
| 低内存部署           | 遵守串行构建，优先外部构建镜像；记录运行和备份峰值                                   | 上线前    |
| 移动端操作           | 验证拍照上传、表单、筛选和搭配查看；无需重新设计整站                                 | 每批验收  |

这些是开发与验收工作，不需要使用者预先选择 SDK、数据库表名、缓存算法或容器内存数值。第 9 节已确认，可按批次 A 开始实现；AI 和天气实测穿插在相应批次前，避免一次性开通不需要的服务。
