# 智能衣柜集成评估与 AI 约束

评估日期：2026-10-20。适用场景：家常账（HomeData）、两人家庭、衣物数量较少、现有服务器 2 核 2 GB。

## 结论

建议将智能衣柜作为家常账内部模块开发，沿用 Vue、NestJS、PostgreSQL 和现有 worker。借鉴 AIWardrobe 的衣物属性、天气辅助、库存推荐与解释设计，不并行部署其整套 React、FastAPI、SQLite 系统。

首版闭环是：拍照或手动录入 → 核对标签 → 找到自己的衣物 → 根据天气与场景选择现有搭配 → 可选关联购物账目或养护待办。AI 是录入和选择的辅助；关闭 AI 后，基础衣柜仍应可用。

事实边界：本评估核对的是当前工作区代码、项目部署记录、AIWardrobe 源码及供应商官方资料；未测量线上服务器实时资源，未调用付费模型验证效果。用户说明的已部署状态作为现状；README 中部分部署待验收描述可能滞后，不据此认定线上不可用。

## 一、功能取舍

### 原仓库实际实现

核查版本：`9a25eca94faa4ebe815a9660eeb94e5513532319`。详细实现边界和固定版本证据见 [AIWardrobe 源码研究](research/aiwardrobe-source-review.md)。

| 模块        | 实际行为                                                                    | 需要注意的边界                                                       |
| ----------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 拍照录入    | 上传图片，尝试本地 rembg／外部 remove.bg 抠图，再调用视觉模型提取属性并保存 | 识别失败会阻断上传；不是现有家常账“先给草稿、确认才入库”的模式       |
| 衣物管理    | 衣柜列表、详情、属性编辑和删除等                                            | 单个全局衣柜，缺少账号、成员归属和个人／家庭隔离                     |
| 手动搭配    | 按季节筛选、逐项切换上装／下装／鞋、随机组合                                | 仅前端临时状态，没有持久化收藏或穿着历史                             |
| 天气和地点  | 地点解析、天气查询及缓存                                                    | 无可用天气缓存且外部请求失败时会返回固定模拟天气，不能照搬到生产推荐 |
| 穿搭推荐    | 先按温度／季节筛选，再按目标、幸运色等评分，按类别选高分单品                | 独立挑各类单品，缺少完整组合协调、轮换和洗衣状态；不是 LLM 直接选衣  |
| AI 推荐文案 | 把天气、目标与已选单品交给 LLM 写理由                                       | 无 Key、超时或调用失败时可回退规则文本                               |
| 星座与语音  | 星座运势／幸运色、语音输入目标                                              | 可从本家庭首版删除，不影响衣柜主流程                                 |
| 虚拟试穿    | 对接用户自配的外部 Try-On HTTP 接口                                         | 默认关闭，没有提供可本地直接运行的试穿模型                           |
| 配置与部署  | React 前端、FastAPI、SQLite、本地图片，支持 Docker                          | 图片静态公开；有网页触发安装依赖接口；不宜作为已有家庭系统的权限基础 |

上传、推荐与天气实现分别见[上传源码](https://github.com/leoz9/AIWardrobe/blob/9a25eca94faa4ebe815a9660eeb94e5513532319/backend/api/upload.py)、[推荐源码](https://github.com/leoz9/AIWardrobe/blob/9a25eca94faa4ebe815a9660eeb94e5513532319/backend/services/recommendation.py)、[天气源码](https://github.com/leoz9/AIWardrobe/blob/9a25eca94faa4ebe815a9660eeb94e5513532319/backend/services/weather.py)。

从全局衣柜、自动识别后直接保存、静态图片与可用性兜底推断，其设计更适合单用户便捷使用；这不是作者意图的确认。它与家常账的成员权限、草稿确认和真实账目要求不相同。根本改法是把衣物、图片、推荐都纳入现有账号与家庭领域，并将外部服务失败表达为真实状态，而非只在页面上补一个“选择成员”。

### 建议保留、简化与删除

下表是集成决策，不代表每一项都是原仓库已经具备的能力。

| 能力                               | 集成优先级       | 适合本家庭的范围                                                                     |
| ---------------------------------- | ---------------- | ------------------------------------------------------------------------------------ |
| 衣物照片、分类与详情               | 必须             | 手机拍照、上传、列表、查看、编辑、删除／归档；保留手工录入                           |
| 基础属性与筛选                     | 必须             | 所有人、类别、主色、季节／保暖程度；名称可自动建议，其他信息选填                     |
| 可用状态                           | 必须补充         | 可穿、待清洗／清洗中、收纳、退役；推荐排除不可穿衣物                                 |
| AI 辅助识别                        | 建议首版         | 识别类别、颜色和可见款式，形成可编辑草稿，确认后入柜                                 |
| 根据已有衣物推荐                   | 建议首版         | 一个默认模式；场景选通勤、休闲、运动等，给 1—3 套真实库存组合                        |
| 天气辅助                           | 建议首版         | 手选默认城市、共享天气缓存；天气不可用时可手选冷热和雨天                             |
| 推荐理由                           | 保留             | 解释温度、场景、颜色、可用状态；不需要长篇聊天                                       |
| 收藏搭配                           | 轻量保留或第二期 | 保存衣物 ID 组合，以后直接复用，减少重复 AI 调用                                     |
| 自动抠图                           | 可不要           | 首版使用统一背景拍照、手动裁剪；抠图失败不影响录入                                   |
| 三种推荐策略                       | 可简化           | 首版仅库存优先，不提供“缺什么买什么”的自动购物倾向                                   |
| 语音目标输入                       | 可不要           | 短文本、场景按钮或手机系统键盘语音即可                                               |
| 星座、运势、幸运色                 | 不建议           | 与衣物管理和家庭记账的主要目标无关，还引入额外请求和生成内容                         |
| AI 虚拟试穿                        | 暂不做           | 外部试穿接口、照片隐私、生成费用与等待时间均增加复杂度；生成图也不能验证真实合身程度 |
| 多语言、另一个主题／设置系统       | 不迁移           | 沿用家常账的中文界面、账号与配置方式                                                 |
| 页面内安装本地模型依赖             | 不迁移           | 不向业务页面开放服务器安装依赖的能力                                                 |
| 向量搜索、RAG、Agent、多轮衣橱聊天 | 暂不做           | 少量衣物用数据库筛选和简短结构化上下文已经足够                                       |

首版不应要求把所有旧衣服一次录完。先录经常穿的 20—40 件，验证能否减少找衣服和选搭配的时间，再补全。这个数量是试用建议，不是系统硬限制。

### 推荐页面结构

在现有应用内新增“衣柜”入口，页面提供“我的衣物”“搭配”两个视图。新增／编辑使用抽屉或独立表单；详情里提供“关联账目”“建立养护待办”。家庭视图按成员筛选，个人衣柜默认只展示本人。移动端现有五个主导航不宜直接挤成六个等宽入口，可把衣柜先放首页快捷入口或“更多”。

## 二、与家常账的联动

### 1. 服饰账目与衣物档案

当前统一支出分类已经包含 `CLOTHING / 服饰`，不需要新增平行的购物账本。

- 从一笔服饰支出进入“添加衣物”，预填购买日期、可见的账目名称，并关联原支出。
- 从衣物详情选择“关联已有支出”，或打开预填的新增支出表单，由用户确认保存。
- 不因录入衣物自动新增消费：旧衣、礼物、赠品都可能没有支出，也可能已经记过账。
- 付款人、衣物所有人和费用归属分别表达。例如 A 付款给 B 买衣服，衣物归 B 且仅 B 可见，账单仍记录在 A 的账本；不设置衣物家庭共享范围。
- 一笔订单可能对应多件衣物；首版允许多件衣物关联同笔支出，但不自动把整单金额计入每件。需要每件成本时再引入明确的金额分摊。
- 退款沿用原账本链路。退款不等于衣服已经退回，也不应自动删衣物；可提示用户核对状态。

这些边界来自现有 Expense、Refund、ReceiptLink 与家庭统计口径。衣柜只是资产／物品视角，财务金额仍以原账本为准。

### 2. 养护待办与站内提醒

“羽绒服送洗”“换季收纳”“退货截止日”“取回干洗衣物”可预填现有 Task，由用户确认日期与负责人后建立。首版在待办说明中放衣物引用即可；需要可靠跳转时再新增结构化关联，不提前建设通用事件平台。

现有固定费用模块只适合真实的周期付款，不适合表示洗衣、换季这类非财务任务。完成养护待办是否更新衣物状态，也应有明确动作，不能把“完成任务”一概视为“已经可穿”。

### 3. 首页、报表和家庭权限

- 首页可以显示衣柜快捷入口、已保存的今日搭配、关联养护待办；打开首页不自动调用 AI。
- 原报表继续统计服饰净支出；后续增加衣物数量、闲置情况。穿着次数需要用户主动确认，不能把“被推荐一次”算作穿过。
- 单次穿着成本仅在购买成本／分摊与穿着记录可靠时展示；未知成本和零穿着分别标记，不输出误导性数值。
- 衣物只对所有人本人开放。代购只设置衣物所有人，不授予购买者后续访问权；账目和票据仍沿用账本自身的可见范围。
- 现有访客分享是受限统计快照，首版不扩展成衣柜照片公开分享。

目前仓库没有独立的天气服务，天气属于新能力；首页日历和待办已有基础，不能把已有日历当作已具备行程识别或天气联动。

## 三、最小技术集成

### 可复用与需扩展的代码

| 现有位置                                    | 已有能力                                          | 衣柜的最小改动                                   |
| ------------------------------------------- | ------------------------------------------------- | ------------------------------------------------ |
| `apps/web/src/App.vue`                      | 页面入口、个人／家庭空间                          | 新增衣柜视图和跨页面跳转参数                     |
| `packages/contracts/src/index.ts`           | Zod 共享契约与服饰分类                            | 衣物、搭配、AI 草稿契约                          |
| `apps/server/src/modules/*`                 | NestJS 业务模块及权限惯例                         | 新增 wardrobe 模块，复用会话和家庭校验           |
| `apps/server/prisma/schema.prisma`          | PostgreSQL、Account、Family、Expense、Task、AiRun | 新增衣物／图片／搭配及必要关联                   |
| `modules/ledger/receipt-storage.service.ts` | 私有文件、文件类型检查、哈希                      | 复用存储模式；衣物图片使用独立资源类型和鉴权     |
| `modules/ai/ai.service.ts`                  | 幂等、DB 队列、每日额度、有限重试、失效恢复       | 显式增加衣物识别与搭配处理器，不把衣物假装成票据 |
| `modules/ai/ai-provider.ts`                 | OpenAI 兼容请求、JSON 解析与 Zod 校验             | 衣物和搭配 schema，按能力选择模型与参数          |
| `apps/server/src/worker.ts`                 | 串行 AI 调度、独立提醒扫描                        | 复用现有 worker，不新增 Redis 或 Celery          |

现有 AiRunType 只有票据识别与报表分析，AiService 以“票据，否则分析”分支处理。增加任务类型时必须改为明确分派，否则新任务会错误进入报表分析。现有额度中的“失败释放”是应用额度行为，不能据此断言上游服务没有计费。

现有配置只声明 `disabled / deepseek`，虽然底层请求是 OpenAI 兼容格式，也不能把设置换成通义视为已完成适配。应将凭证、base URL、model、是否支持视觉／结构化输出／思考参数按能力配置，允许衣物识别使用不同供应商，同时保持现有票据和报表行为稳定。首版只增加确实需要的适配器即可。

### 数据最小集合

- 衣物：所有人、可选共享家庭、名称、类别、主色、季节／保暖标签、使用场景、状态、图片、可选购买日期／品牌／尺码／位置、创建更新时间与版本。
- 图片：私有存储键、内容哈希、大小、尺寸；主图与缩略图。不要直接使用 Receipt 表，以免继承错误的票据权限和账目依赖。
- 搭配：所有人、衣物 ID 列表、场景、可选天气快照、说明；保存前校验所有衣物的权限和状态。
- 支出关联：可选，允许一笔支出关联多件衣物；首版无需金额分摊。
- 穿着记录：可后置；保留后续扩展空间，不强制每天打卡。

对于少量衣物，普通索引、分页与枚举筛选即可。不要先建立向量数据库和微服务架构。

衣物类别需要覆盖独立外套、上装、下装、连衣裙／连体、鞋和可选配饰；搭配结构区分“连衣裙＋鞋”与“上装＋下装＋鞋”，按天气叠加外套。不能直接要求所有组合都有上装和下装，也不能把每类最高分单品拼起来就视为协调搭配。可先枚举少量完整组合，再按颜色兼容、温度和场景评分。

## 四、AI 能力边界与低价方案

### 优先级

1. **先验证现有 DeepSeek 接入。** 当前代码默认视觉模型是 `deepseek-flash`。最新[官方视觉文档](https://api-docs.deepseek.com/guides/vision/)明确支持图片和 OpenAI 兼容 Chat Completions；不能沿用早期“DeepSeek API 不能看图”的结论。但衣物提示词、结果准确率和真实账号可用性仍需样本实测。
2. **通义 Flash 作为低价候选。** [官方模型资料](https://help.aliyun.com/zh/model-studio/vision-model)列出 `qwen3.5-flash` 的图像输入能力；[官方价格表](https://help.aliyun.com/zh/model-studio/model-pricing)北京区域、输入不超过 128K 时为输入 0.2 元／百万 Token、输出 2 元／百万 Token。采购和上线时复核模型可用性及地域价格。
3. **难图再选更强视觉模型，或让用户手动修正。** `qwen3-vl-plus` 在同一价格表的北京区域、输入不超过 32K 时为输入 1 元／百万 Token、输出 10 元／百万 Token。每次纠错都自动升级模型并非必要；手动确认往往更划算。
4. **天气、库存过滤、排除脏衣服、生成拼图都不需要大模型。** 首版先以规则产出候选，再由文本模型结合天气、场景和用户想法选择候选并解释；模型不能创建候选外衣物。

上述是当前查到的可用方案，不声称某一家在所有情况下最便宜或准确。家庭低频使用时，复用已配置服务节省的维护成本，可能高于供应商之间几角钱的价差。

### 按动作拆分

| 动作         | 推荐实现                                                                 | 降级                                               |
| ------------ | ------------------------------------------------------------------------ | -------------------------------------------------- |
| 衣物识别     | 一张单品图调用一次云端视觉模型，保存结构化标签                           | 手动填写类别和颜色，继续入柜                       |
| 衣物抠图     | 首版不依赖；手动裁剪、统一背景                                           | 原图照常使用；后续可手机预处理或本机离线批处理     |
| 天气         | 普通天气 API，缓存 30—60 分钟                                            | 展示更新时间，手选天气／冷热；不让 AI 编造实时天气 |
| 搭配候选     | SQL 筛选所属人、可穿状态、季节与场景，再按规则评分                       | 规则组合或收藏搭配                                 |
| 推荐说明     | 用户点击时把穿搭想法、天气、场景和有限候选提交现有文本模型生成选择与理由 | 未配置、超额、超时或调用失败时显示规则理由         |
| 搭配展示     | 浏览器 CSS／Canvas 把已有衣物图片组合                                    | 直接并列显示图片，无生成图费用                     |
| 真实人体试穿 | 暂不做                                                                   | 搭配板；如以后接入，单独启用并另设预算             |

[Open-Meteo](https://open-meteo.com/en/pricing)提供非商业免费方案，仍需遵守限额和署名要求。两人同城共享缓存足够；目标服务器的实际可达性需验证，无须让每个用户反复自动定位。

### 必须执行的功能约束

- **人工确认**：AI 仅提交草稿；类别、颜色、场景和保暖程度可编辑。不凭照片确定真实面料成分、精确尺码、价格、品牌或洗护规范；洗标信息需要另拍洗标或人工输入。
- **推荐必须受库存约束**：返回的衣物 ID 必须存在、当前有权访问且可穿，套餐结构合理；不跨成员借衣，不把已退役衣物、脏衣物或虚构商品放进结果。缺少必要品类时明确说明，不凑完整搭配。
- **选择与执行分离**：选择搭配不代表已经穿过；AI 不自动下单、不自动记账、不替用户新增任务、不自动修改清洗状态。
- **主动触发**：只有用户点击衣物识别或生成推荐才调用模型；不在首页、列表、天气刷新或日期变化时创建模型任务。
- **控制输入**：单张单品图优先；客户端压缩到约 768—1024 像素长边、目标 100—300 KB，识别困难时允许重拍。后端仍验证真实格式、解码后的像素总量、大小及权限；移除 EXIF。压缩文件体积不会自动保证相同视觉 Token 成本。
- **限制上下文**：衣物识别只传用户选择的单张图片；推荐只传规则候选的名称、类别、颜色、层次、最多 80 字的衣物穿搭建议和 ID，以及必要天气、场景和用户想法，不发送衣物原图、账本或其他成员衣物。
- **异步与有限重试**：沿用串行 worker，并发设为 1；30—60 秒超时起步，最多自动重试一次。页面可离开，回来读取结果；失败保留原照片和手工路径。
- **防止重复花费**：识别以所属用户、图片哈希、识别版本复用；日常生成一次请求，整段旅行聚合为一次请求。展示与保存时仍重新校验衣物状态和权限。
- **预算**：每人每日衣物识别上限 10 次、穿搭推荐上限 5 次；旅行整段只占一次推荐额度。供应商账单才是实际成本依据。
- **隐私**：Key 仅在服务端；云端只接收用户主动提交的单品图或必要标签。衣物保持所有人私有，不把私有图片改为公开 URL 来方便模型读取。

### 可核算的费用示例

以下为假设，不是账单或准确率承诺。以 `qwen3.5-flash` 上述价格、非思考、无免费额度抵扣计算：

- 100 件衣物，每次 2,000 输入 Token（包括图片处理后的 Token）+ 300 输出 Token：`100 × (2000 × 0.2 + 300 × 2) / 1,000,000 = 0.10 元`。
- 两人各每天一次推荐，30 天共 60 次，每次 4,000 输入 + 600 输出：`60 × (4000 × 0.2 + 600 × 2) / 1,000,000 = 0.12 元`。
- 两者合计约 0.22 元；实际还会受视觉 Token、提示词长度、重试、纠错和价格变化影响。如果改用上述更强视觉模型，同样 100 次识别的算术示例是 0.50 元。

这表明低频场景应优先减少实现和维护负担，不必为压低到“完全零调用费”在 2 GB 服务器部署推理模型。免费额度不作为长期运行前提，最小充值额也不等于实际用量费用。

## 五、2 核 2 GB 的资源约束

现有 Compose 已包含 PostgreSQL、API、worker、Nginx／Web；部署手册明确记录过并行构建 OOM。无法仅凭两个人使用就断言内存充足：内存峰值更多受图片解码、模型装载与构建影响。

建议约束如下：

1. 不常驻本地 LLM、视觉模型、rembg／ONNX 推理服务；不新增 Python 服务、Redis 或第二套数据库。不是声称轻量抠图绝对跑不了，而是在现有业务资源未知时不把它作为生产依赖。
2. 图片以单张队列处理，限制像素和请求大小，列表用缩略图、分页、懒加载。不要只限制 JPEG 文件大小，几十 MB 解码内存也可能来自很小的压缩文件。
3. 数据库只存标签、关联和存储键，图片保存在私有持久卷。衣物照片纳入现有异地备份／恢复范围；不只备份数据库。
4. 假设 300 件衣物，每件一张 300 KB 主图和一张 30 KB 缩略图，约占 99 MB（十进制），未含备份和原始手机照片。默认不长期保存未经压缩的大原图，替换图片需清理孤立文件。
5. 优先本地或 CI 构建镜像，再部署到服务器；继续遵守现有串行构建约束。部署前记录 `free` 和 `docker stats`，覆盖空闲、上传、识别、推荐、备份场景，确认无 OOM 且现有记账和提醒不受影响，再确定容器限制。

不为本评估给出未经测量的精确新增内存承诺，也不把 swap 当作模型运行容量。

## 六、分期及验收

### 第一期：基础衣柜和辅助录入

交付衣物管理、所有人与共享权限、压缩图片、筛选、状态、AI 草稿和手工降级、可选支出关联。无需天气和推荐即可使用。验收：关闭 AI 可录衣；A 无法读取 B 的私有图片；改草稿后才入库；关联已有支出不重复记账；手机浏览和现有账本稳定。

### 第二期：天气与库存搭配

交付城市设置、天气缓存、规则候选、用户触发的 AI 选择与理由、收藏搭配、待办入口。验收：不生成不存在／无权／不可穿衣物；天气失败可继续；刷新页面不新增模型调用；更改衣物状态使推荐失效或保存时被拦截；AI 调用不阻塞提醒。

### 第三期：基于真实使用补充

仅在有足够穿着记录和成本数据后增加闲置提醒、单次穿着成本、旅行打包清单；抠图视录入体验决定。虚拟试穿、星座和复杂 Agent 不作为默认建设目标。

建议上线前用约 20 张自家衣物照片做一次小样本验证，覆盖黑色、白色、花纹、褶皱和复杂背景，记录类别／颜色纠错率、延迟、失败率和真实 Token。该样本用于决定是否采用供应商，不代表已完成测试。
